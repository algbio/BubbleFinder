Advanced interfaces

Choosing a C++ interface

OGDF is a C++ library for graph algorithms. SPQR-Rust provides two C++ interfaces for two priorities: spqr::ogdf_compat to simplify the transition from existing OGDF code, and spqr for code where performance is the priority, with compact edge values and fewer checks when accessing arrays.

Your priorityInterfaceWhat it provides
Simplify the transition from OGDF.spqr::ogdf_compatKeeps familiar calls such as e->source() and e->target(). Arrays linked to a graph grow automatically when accessed after the graph grows. See migration steps.
Reduce storage and repeated checks in C++ code.spqrStores edges as compact integer IDs and accesses arrays without querying the graph's size. You manage array sizes as the graph grows. See memory and runtime costs.

Both interfaces use the same Rust SPQR builder and require an SPQR-Rust graph. To retain OGDF elsewhere in your library, see Keeping your OGDF graph.

Memory and runtime

Both interfaces use 32-bit IDs and read input-edge endpoints through the same Rust function.

Operationspqr::ogdf_compatspqr
Store one C++ edge valueTypically 16 bytes with 8-byte pointers: its ID and a pointer to the graph.4 bytes: its ID.
Index a node/edge array constructed with an input graphQueries the graph's size before indexing, and grows the array if needed.Does not query the graph's size. Writable indexing can still grow the array.
Read a real skeleton edge with source(), target() or forEachEdge()Reads the endpoints stored in the skeleton.Reads the original input edge's source to match the input endpoint order.

One million stored edge values occupy 16 MB with spqr::ogdf_compat and 4 MB with spqr. Total memory also includes the Rust graph and tree, other C++ objects and reserved array capacity.

The runtime effect depends on how often your code performs these operations. Compile both C++ and Rust with optimisation enabled.

Build and link

Build the library from its repository:

Terminal
git clone https://github.com/algbio/spqr-rust
cd spqr-rust
cargo build --release

On Linux, Cargo produces target/release/libspqr_rust.a (static) and target/release/libspqr_rust.so (shared). C functions (FFI) are declared in include/spqr_tree.h.

Download the C++ example and compile it from the repository root:

Terminal
c++ -O3 -std=c++17 spqr-example.cpp -I include -L target/release \
  -Wl,-rpath,'$ORIGIN/target/release' -lspqr_rust -o example
./example

Changes to your code

Most changes needed to port OGDF code apply to both interfaces.

  1. Include spqr_compat.hpp and link libspqr_rust using the build command.
  2. Replace the OGDF types used by the SPQR routine with those from the chosen namespace: Graph, node, edge, NodeArray<T>, EdgeArray<T> and StaticSPQRTree.
  3. Update the calls below. Both interfaces implement part of OGDF's API. Check any other methods you use in the header reference.

For example, the same input-graph operation becomes:

C++: spqr
spqr::Graph graph;
auto a = graph.newNode();
auto b = graph.newNode();
auto edge = graph.newEdge(a, b);
auto source = graph.source(edge);
C++: spqr::ogdf_compat
spqr::ogdf_compat::Graph graph;
auto a = graph.newNode();
auto b = graph.newNode();
auto edge = graph.newEdge(a, b);
auto source = edge->source();

For tree edges, use tree.tree().source(e) and tree.tree().target(e). For skeleton edges, create auto skeleton = tree.skeleton(tn), where tn is a tree node, then use skeleton.getGraph().source(e) and skeleton.getGraph().target(e).

Behavior when switching interfaces

source and target name the stored endpoints of an undirected edge.

  • Arrays created with a graph in spqr::ogdf_compat grow when accessed after the graph grows. With spqr, resize before const reads, size() or iteration. Writable indexing extends the array only as needed for that index.
  • spqr matches real skeleton edge endpoints to the input order. spqr::ogdf_compat keeps the stored skeleton order. source and target can therefore be exchanged between interfaces.

Keeping your OGDF graph

To keep your library's existing ogdf::Graph API, convert the graph inside the SPQR routine:

  1. Copy each biconnected block into an SPQR-Rust graph, numbering its vertices from zero.
  2. Keep mappings from the copied vertices and edges back to the OGDF objects.
  3. Compute the tree and use those mappings when returning results.

Copying adds a pass over the vertices and edges and storage for a second graph. This applies to both interfaces. Alternatively, change the graph types in your public API and update its callers.

Reading the tree

Use forEachAdj for neighbours and skeleton.forEachEdge for skeleton edges, without building temporary neighbour vectors or skeleton graphs. tree.flatView() reads Rust's arrays without copying. Keep the graph and tree alive while using these views.

spqr::ogdf_compat example · spqr example. Both use the illustrated graph and print S: 1, P: 1, R: 2, original edges: 14. Use the build command with the corresponding source filename.

Both interfaces support direct construction with StaticSPQRTree(graph), or compression and reconstruction with StaticSPQRTree(graph, contractible, length). The contractible mask has one byte per vertex: zero prevents series removal, while a nonzero value allows it at degree two. length is the mask length.

ogdf_compat.hpp is an alternative filename for spqr_compat.hpp. Declarations: SPQR-Rust header. Original interfaces: OGDF Graph, NodeElement, EdgeElement and StaticSPQRTree.

Lower-level C++ wrapper

spqr_rust_wrapper.hpp defines classes owning Rust graphs and decomposition results: RustGraph, RustSPQRResult, RustBCTree and RustConnectedComponents. They release memory on destruction and support moves rather than copies. Both C++ interfaces use them internally.

This C++17 example builds a complete graph on four vertices. Its tree has one R node:

spqr-example.cpp
#include "spqr_rust_wrapper.hpp"
#include <iostream>

int main() {
    spqr_rust::RustGraph graph;
    graph.addNodes(4);
    for (const auto& edge : {std::pair{0u, 1u}, {0u, 2u}, {0u, 3u},
                            {1u, 2u}, {1u, 3u}, {2u, 3u}}) {
        graph.addEdge(edge.first, edge.second);
    }

    spqr_rust::RustSPQRResult result(graph);
    std::cout << result.treeLen() << "\n";
}

The output is 1. In C, free results with spqr_result_free and graphs with spqr_graph_free. The tree returned by spqr_result_tree belongs to the result. Release text from spqr_format_to_string with spqr_string_free.

Identifier size: 32 or 64 bits

The standard Rust types and both C++ interfaces use 32-bit IDs (4 bytes) for vertices, edges and tree nodes. The optional spqr_rust::wide module provides separate 64-bit types (8 bytes) for larger ID ranges. The C functions ending in _u64 also take separate 64-bit graph and tree types.

Rust
use spqr_rust::wide::{build_spqr, Graph, NodeId};

Download a complete 64-bit example.

InterfacePurpose
spqr_rustDefault 32-bit graph and SPQR tree types. See Getting started.

compress_dense64-bit compression from a record containing its own edge and mask arrays.
compress_borrowed_dense64-bit compression using consecutive IDs and your existing edge and mask arrays.
compress_borrowed_remappedFor widely spaced input IDs, compress only vertices that appear in the edge list, then restore the original endpoint IDs.
reconstruct_wide::reconstructRecover the full 64-bit tree from the tree of the compressed graph, its saved reductions and the vertex mapping.

In compress_borrowed_remapped, an active vertex is a vertex present in the edge list. If the mask has one entry per active vertex, its entries follow their sorted original IDs. Otherwise, positions in the mask are original vertex IDs. Missing entries in this second form prevent series removal through those vertices. The input n_nodes must exceed the largest original vertex ID.

The general verify and spqr_format modules use the ordinary 32-bit graph and tree types. Their functions do not accept wide::Graph or wide::SpqrTree. See the API signatures before combining interfaces.

Compression through C

As described in Compression, the core is the graph left after replacing paths and parallel edges. Macros record those replacements so the full tree can be recovered.

A SpCompressHandle* owns the compression data. sp_compress_get_tree returns a SpCompressTreeView borrowing its macro and core arrays. Keep the handle alive while using the view.

Function familyPurpose
sp_compress_ffiCompress explicit input-edge records. Set build_core_spqr to request an SPQR tree of the compressed graph.
sp_compress_indexed_ffiRead two arrays containing the first and second endpoint of each edge. Original edge IDs are the array positions. sp_compress_indexed_ffi can use a specialised method for shortening paths through vertices with two incident edges.
sp_compress_timed_ffiReturn compression/core timing measurements in SpCompressTimings.
sp_compress_get_tree, sp_compress_get_core_spqrRead the saved reductions, compressed graph and its optional SPQR tree without copying them.
sp_compress_core_node_invRead the array mapping each vertex ID in the core graph to its vertex ID before compression.
sp_compress_reconstruct_ffi, sp_compress_reconstruct_with_timings_ffiCompress the graph, build the core tree and reconstruct the full tree. The timing variant also reports statistics and elapsed times.
sp_compress_from_snapshot_ffiRestore a handle from a snapshot of the compression state.
sp_compress_freeRelease a compression handle.

Check the returned handle for null and call sp_compress_success before reading results. Copy arrays before freeing the handle if you need to retain them. Free reconstruction results with spqr_result_free, or spqr_result_free_u64 for 64-bit results.

The 64-bit compression calls use names ending in _ffi64 or _ffi_u64. Use the input and output types in their declarations, including SpCompressTreeView64 and SpCompressStats64. The exact function arguments and record fields are listed in sp_compress.h and the Rust FFI reference.

spqr-compression.c
#include "sp_compress.h"
#include <assert.h>
#include <stdio.h>

int main(void) {
    const SpCompressInputEdge edges[] = {
        {0, 1, 0}, {0, 2, 1}, {0, 3, 2}, {1, 2, 3}, {1, 3, 4},
        {2, 3, 5}, {0, 4, 6}, {0, 5, 7}, {1, 4, 8}, {1, 5, 9},
        {4, 5, 10}, {0, 6, 11}, {6, 7, 12}, {7, 1, 13}
    };
    const uint8_t contractible[8] = {1, 1, 1, 1, 1, 1, 1, 1};
    SpCompressHandle* handle = sp_compress_ffi(
        8, edges, 14, 13, contractible, 8, 1);
    assert(handle && sp_compress_success(handle));
    SpCompressTreeView view = sp_compress_get_tree(handle);
    assert(view.core_edges_len > 0);
    printf("Core edges: %llu\n", (unsigned long long)view.core_edges_len);
    sp_compress_free(handle);

    SpqrResult* result = sp_compress_reconstruct_ffi(
        8, edges, 14, 13, contractible, 8);
    assert(result);
    const SpqrTree* tree = spqr_result_tree(result);
    uint32_t s, p, r;
    spqr_tree_count_by_type(tree, &s, &p, &r);
    assert(s == 1 && p == 1 && r == 2);
    printf("S: %u, P: %u, R: %u\n", s, p, r);
    spqr_result_free(result);
    return 0;
}

Download the C example. Compile it like the C++ example, using cc -std=c11 and the C filename. It reports 11 core edges and reconstructs a tree with S=1, P=1 and R=2.

Snapshots: compression state in memory

A snapshot captures compression state in memory: macros, the core graph, input endpoints, statistics and an optional core tree with its vertex mapping.

sp_compress_from_snapshot_ffi copies a SpCompressSnapshotView into a new compression handle. Keep the input arrays valid during the call and release the handle with sp_compress_free.

The calling application handles saving snapshots to disk and reading them back.

sp_compress_from_snapshot_ffi accepts the 32-bit snapshot records declared in sp_compress.h.

Command-line example

The repository includes spqr_cli for inspecting a graph from an undirected edge list:

Terminal
cargo run --release --bin spqr_cli -- spqr-graph.txt

Download the example edge list. Each nonempty line gives two vertex names or IDs, separated by whitespace. Empty lines and lines starting with # are ignored. The reader assigns consecutive internal vertex IDs to the distinct input names.

The program processes the connected component with the most vertices. It must be biconnected. Isolated vertices cannot be specified in the edge-list input.

It prints graph sizes and tree counts, plus the decomposition when it has at most 20 tree nodes. For graphs with several blocks, build one SPQR tree per block in the library.

Runtime settings and validation

OMP_NUM_THREADS sets the thread count. If unset or invalid, the library tries RAYON_NUM_THREADS, then defaults to one thread. The count is capped by available hardware threads and cached on first use.

CANONICALIZE_ROOT_ENABLED selects a consistent tree root, with C getters and setters. Diagnostic functions report cycle-handling counters and compression/reconstruction timings. See the C function index.

cargo test runs the default test suite. Additional tests marked as ignored can be run explicitly with cargo test --release -- --ignored. In tests that use SPQR_NUM_RANDOM, this environment variable sets the number of random graphs to generate.
